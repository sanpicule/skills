# requirements-design-generator

**未システム化の業務**について、ユーザーが持つ参考資料（Google ドキュメント、スプレッドシート、PDF、Word、Excel、マニュアル、議事録、業務手順書、帳票サンプル等）を読み解き、そこから業務ルール・データ構造・運用フローを抽出して **システム化のための要件定義書と設計書（初版）** を作成するスキル。

## いつ使うか

- 「この資料群からシステムの要件をまとめて」と依頼されたとき
- 紙・Excel・口伝で運用されている業務をシステム化したいとき
- 顧客から提供された業務資料を整理して提案・見積の前提を整えたいとき
- 既存業務の暗黙知を形式知化して、開発に渡せる仕様に落としたいとき

## 入力

- **対象ディレクトリ**: 参考資料が格納されているローカルパス、または Google Drive のフォルダ
- **資料の形式（混在可）**:
  - Google ドキュメント / スプレッドシート / スライド（URL またはローカルにダウンロード済み）
  - Word (.docx) / Excel (.xlsx) / PowerPoint (.pptx)
  - PDF
  - テキスト / Markdown / CSV
  - 画像（帳票・画面イメージのスクリーンショット等）

## 実行手順（全体像）

```
[1] ヒアリング (メイン: AskUserQuestion で対話)
        ↓
[2] 資料読み込み (SubAgent を並列起動 → 構造化サマリだけメインに戻す)
        ↓
[3] 業務知識の統合 (メイン: 矛盾突合・推測補完)
        ↓
[4] ドキュメント生成 (メイン: テンプレート展開で 5 ファイル出力 ※QA.md 含む)
        ↓
[5] ユーザーへの報告 (メイン: 推測箇所・矛盾・追加ヒアリング項目を提示)
```

設計意図: **対話と統合はメイン、読み込みは SubAgent**。これにより、(a) ユーザーと自然に対話を続けつつ、(b) 大量資料でメイン文脈を埋めず、(c) 並列化で待ち時間を短縮する。

### ステップ 1: 対象範囲のヒアリング（必須・最初に実施）

ディレクトリ構成や資料の性質はプロジェクトごとに異なるため、**まず `AskUserQuestion` ツールでユーザーに以下を確認する**。確認なしに勝手に走り出してはならない。

確認すべき項目:

1. **対象ディレクトリ**: 参考資料が置かれているパス（ローカル or Google Drive）
2. **格納場所の種類**:
   - ローカルフォルダ（`.docx`, `.xlsx`, `.pdf` 等のファイル実体）
   - Google Drive フォルダ（Google ドキュメント／スプレッドシート等。MCP で取得）
   - 両方混在
3. **システム化のスコープ**: 業務全体か、特定の業務領域・サブシステムのみか
4. **想定読者**: 社内開発チーム / 外部ベンダー / 経営層 など（記述粒度に影響）
5. **出力先**: 既定 `<対象>/_output/` 配下に保存。変更したい場合は指定
6. **既知の前提**: 利用予定の技術スタック・連携先システム・予算/期間制約があれば

ヒアリング後、対象ディレクトリの**ファイル一覧を取得**し、ユーザーに提示してから**どの資料を調査対象とするか確認**する。資料が多い場合は除外候補（古いバージョン、メモ書き等）も提案する。

### ステップ 2: 資料の読み込み（専用 SubAgent を並列起動）

**設計方針**: 資料本文をメイン文脈に積まない。専用 SubAgent `business-document-analyzer` に並列で読ませて**構造化サマリのみ**回収する。これによりメイン文脈を節約し、後段の統合・対話に余力を残す。

#### 2-1. 使用する SubAgent

- **`business-document-analyzer`**（`~/.claude/agents/business-document-analyzer.md`）
  - 業務資料の読み込み・抽出・構造化サマリ化に特化した専用エージェント
  - 出力フォーマット（資料サマリ / アクター / 業務フロー / 業務ルール / データ項目 / 用語 等）は SubAgent 側のシステムプロンプトで規定済み
  - Read / Bash / Glob / Grep / Google Drive MCP を利用可能

#### 2-2. 分割方針

- **1 SubAgent = 1 資料**（または密接に関連する 2〜3 本）を担当
- 資料が 2 本以下＆軽量（数ページ程度）なら、メインで直接読んでもよい
- それ以上、または巨大ファイル（数十ページ PDF、複数シート Excel 等）が含まれる場合は**必ず** SubAgent 並列化を使う
- **並列起動**: 1 メッセージ内で複数 `Agent` tool use を発行する（逐次起動は禁止）

#### 2-3. 呼び出し方

`Agent` ツールに以下を指定して起動する:

- `subagent_type`: `business-document-analyzer`
- `description`: `資料Xを構造化サマリ化` のような短い説明
- `prompt`: 下記テンプレートで担当資料と背景情報を渡す

```
担当資料: <資料パス or Drive URL or ファイル ID>
形式: <docx / xlsx / pdf / Google Doc / ...>

# プロジェクト背景
- 業務領域: …
- 想定読者: …
- 既知の用語: …（あれば）
- 既に判明している前提: …（他資料から得た情報があれば）

# 依頼
担当資料を読み、システムプロンプトに定められたフォーマットで構造化サマリを返してください。
```

出力フォーマット・推測ルール・マスキング方針・「前置きを書かない」等は **SubAgent 側に既に組み込まれている**ので、呼び出し側で繰り返し指定する必要はない。

#### 2-4. メインでの統合

- 各 SubAgent から返ってきたサマリ（構造化済み）を集約
- 資料間で**重複/矛盾**する記述を突き合わせる（矛盾は両論併記して後段で確認）
- SubAgent から「呼び出し元への質問・追加調査依頼」が返ってきた場合は、ユーザーに転送するか追加 SubAgent で調査する

**注意**:
- 古いバージョン同士で矛盾がある場合は両方記録し、ユーザーに確認を求める
- SubAgent は最終テキスト 1 メッセージのみ返す。フォーマットが乱れていたら再呼び出しで修正させる

### ステップ 3: 業務知識の構造化（メインで実施）

SubAgent から集まったサマリを統合し、以下を抽出・整理する。**資料に書かれていることと、推測で補った内容を必ず区別する**。

- **業務概要**: 何のための業務か、誰が、いつ、何を使って実施するか
- **登場人物（アクター）**: 役割・権限・関心事
- **業務フロー**: 開始トリガー → 各ステップ → 終了条件、分岐・例外
- **業務ルール**: 計算ロジック、判定条件、禁止事項、SLA、運用カレンダー
- **データ項目**: 取り扱う情報の項目、型、必須/任意、入力ソース、保持期間
- **帳票・成果物**: 出力されるドキュメント、報告書、画面イメージ
- **既存ツール・システム連携**: 現状利用中の Excel、外部サービス、メール運用等
- **課題・要望**: 資料中の「困っていること」「改善したいこと」
- **用語集**: 業界用語、社内用語、略語

### ステップ 4: ドキュメント生成

`templates/` 配下のテンプレートをベースに、以下を出力先に作成:

- `要件定義書.md` — システム化の要件
- `設計書_初版.md` — 業務をシステムに落とすための初期設計案
- `用語集.md` — ドメイン用語の辞書
- `資料インデックス.md` — どの資料の何ページ／どのシートを根拠としたかの索引
- `QA.md` — **作成過程で顧客に確認すべき事項の質問票**（後述 4-1）

既に同名ファイルが存在する場合は、上書きせず `要件定義書.YYYYMMDD.md` のように日付サフィックスで保存する。

各記述には**根拠資料**を `[資料名 / シート名 or ページ番号]` の形式で必ず併記する（例: `[業務手順書_v3.docx / p.12]`）。

#### 4-1. QA.md の生成（必須）

ドキュメント生成と並行して、**作成過程で発生した「ユーザー／顧客に確認しないと確定できない事項」を 1 つの質問票 `QA.md` に集約**する。要件定義書・設計書の本文中に散らばる `> 📝 推測:` `> ⚠️ 要確認:` ブロックや、SubAgent からの「呼び出し元への質問・追加調査依頼」は、すべてこの QA.md に転記する。

**設計意図**: 推測・矛盾・空欄項目を文書本文内のブロックだけに留めると、確認漏れが発生しやすい。1 ファイルにまとめて顧客にそのまま送付できる体裁にすることで、確認の運用負荷を下げる。

##### QA.md に必ず含める項目

要件定義書・設計書の生成中、以下の **いずれかに該当する記述を残すたびに、QA.md にも質問として追記する**:

1. **資料間の矛盾**: 同一トピックで資料 A・資料 B の記述が異なる場合（要件定義書 付録 B と同期）
2. **推測で補った項目**: `> 📝 推測:` ブロックを書いた箇所（要件定義書 付録 A と同期）
3. **資料に書かれていない検討事項**: `> ⚠️ 要確認:` ブロックを書いた箇所
4. **SubAgent からの「呼び出し元への質問」**: business-document-analyzer が返した追加調査依頼
5. **空欄にした項目**: 情報不足で記載できなかった項目（要件定義書 付録 C と同期）
6. **非機能要件の数値が決まらないもの**: 性能・可用性・データ保持期間・予算・期限など

##### QA.md の章立て（優先度別）

| セクション | 内容 | マーク |
| --- | --- | --- |
| A. 最優先（ブロック事項） | これがないと設計に着手できない | `[ブロック]` |
| B. 業務ルールの矛盾・確定要 | 資料間で矛盾している業務ルール | - |
| C. 業務運用フローの未確定事項 | 暗黙運用・例外フロー等 | - |
| D. 現状帳票・運用に関する確認 | 帳票の記号・色分け・略称等 | - |
| E. 非機能要件・プロジェクト計画 | 規模・予算・期限・認証方式等 | - |
| F. 期限・連絡方法 | 回答期限・連絡先 | - |

##### 各質問の必須フィールド

各質問は以下のテーブル形式で記載する（顧客が記入しやすいよう **回答欄を空けておく**）:

| 項目 | 内容 |
| --- | --- |
| 質問 | （具体的な質問文。選択肢があれば (a)(b)(c) で列挙） |
| 関連箇所 | `[資料名 / 該当箇所]`（出典） |
| 影響範囲 | 影響する機能 ID・ルール ID・設計章 |
| 回答 | （空欄。顧客が記入） |
| 補足・コメント | （空欄。顧客が記入） |

##### テンプレート

`templates/qa.md` を使用する。

##### 整合性ルール

- QA.md の **A セクション（ブロック事項）** に含めた質問は、必ず要件定義書 §13（リスク・課題）にも対応するエントリを置く
- 要件定義書 付録 A（推測） / 付録 B（矛盾） / 付録 C（情報不足）の **全エントリは QA.md にも対応する質問として転記**する（漏れがあってはならない）
- QA.md の質問件数は通常 15〜30 件程度。100 件を超える場合はスコープ過大の兆候 → セクション分割やヒアリング会の提案を検討

### ステップ 5: ユーザーへの報告

- 生成したファイルのパス一覧（QA.md を含む 5 ファイル）
- **QA.md の章別質問数サマリ**（A〜F の各セクションで何件の質問を起こしたか）
- **A セクション（ブロック事項）の質問件名一覧**（最優先で回答が必要なものを明示）
- 次のアクション提案（例: 「QA.md をそのまま顧客に送付するか、まずは A セクションだけヒアリング会で潰しに行きますか？」）

2. 現状業務（As-Is）の整理
3. システム化の目的・期待効果
4. ステークホルダー・アクター
5. 用語集（要約版・詳細は別ファイル）

11. 制約事項・前提条件

4. データモデル案（ER 図）
5. 主要ユースケースのシーケンス
6. 外部連携設計案
7. 運用・保守設計案
8. 未確定事項・要検討事項

### QA.md (`QA.md`)

優先度別（A〜F セクション）に、顧客／ユーザーへの質問を 1 ファイルに集約。各質問は「質問 / 関連箇所 / 影響範囲 / 回答 / 補足」のテーブル形式。詳細はステップ 4-1 参照。

## 出力スタイル

- **日本語**で記述
- 業務系の用語は資料の表記を尊重（勝手な言い換えをしない）
- Mermaid で図を埋め込む（業務フロー、ER 図、シーケンス）
- 推測で補った箇所は `> 📝 推測:` ブロックで明示
- 各記述に `[資料名 / 該当箇所]` を脚注的に付与
- 「資料に書かれていないがシステム化に必要な検討事項」は `> ⚠️ 要確認:` ブロックで明示

## やってはいけないこと

- **対象範囲の確認なしに勝手に走り出さない**（ステップ 1 は必須）
- 個人情報・機密情報を生成ドキュメントにそのまま転記しない（構造のみ抽象化）
- 資料に書かれていないことを断定的に書かない（推測ブロック必須）
- 古い資料と新しい資料の矛盾を勝手に解消しない（両論併記してユーザー判断を仰ぐ）
- 1 ファイルでも全件読まない。ボリュームが大きい場合は要約 → 必要箇所のみ精読
- **メイン文脈で raw データを読み込みすぎない**。資料本体は SubAgent で要約し、メインには構造化サマリだけ戻す
- SubAgent を逐次起動しない。独立して読める資料は **1 メッセージで複数 `Agent` を並列発行**する
- **`QA.md` の生成をスキップしない**。推測・矛盾・空欄項目を要件定義書／設計書の本文ブロック内にだけ残すと、確認漏れが起きやすい。必ず 1 ファイルに集約する
- QA.md の質問件名だけ書いて回答欄を埋めない（顧客が記入するためのファイルなので、回答列は **必ず空欄** にしておく）
